# Plan Tasks Skill

Breaks down an epic spec into implementation-ready tasks with dependency ordering and test-first steps.

## Objective

Turn one epic's technical spec into an ordered, dependency-aware list of implementable tasks — each small enough to be one test-first unit of work for `implement-epic`, and traceable back to the acceptance criterion it satisfies (or explicitly marked `Foundation`).

## File Layout

```
{project root}/
├── brainstorm/Epic_PRD.md             (source of epic IDs, via Epic Breakdown)
├── specs/<epic-slug>/spec.md          (input, produced by write-spec)
├── specs/<epic-slug>/tasks.md         (output — Markdown only, generated by this skill)
└── .claude/skills/plan-tasks/
    └── SKILL.md
```

`tasks.md` is the **single** artifact this skill writes — no JSON, no second file. `implement-epic` and `verify-epic` both parse the `### TASK-` blocks in this Markdown.

## Input

`Epic name` — must match an `EPIC-NN` entry in `brainstorm/Epic_PRD.md`'s Epic Breakdown, and that epic must already have a `specs/<epic-slug>/spec.md`. Use the **same `<epic-slug>` that `write-spec` used** for that epic — don't derive a new one. If the spec doesn't exist yet, stop and say so — don't plan tasks from the PRD directly, skip `write-spec`, or improvise a spec on the fly.

## Workflow — state machine

### Phase 0 — Preflight

**Read the shared standards first**, in this fixed order — never directory-listing order, so the prompt prefix stays identical across runs and prompt caching engages:

1. `.claude/_architecture-reference.md`
2. `.claude/_coding-guidelines.md`
3. `.claude/_documentation-standards.md`

Follow their conventions if they exist. If any are missing, proceed but record a note under the task list's Dependency notes recommending `set-standards` be run before further epics are built. Then continue with the checks below.

1. Confirm `specs/<epic-slug>/spec.md` exists for the named epic
   - If not, stop and report: "No spec found. Run /write-spec first."
2. Note the spec's own Confidence Level in the task list header, informationally — same as `write-spec` noted the PRD's confidence. Do not block on it; a spec with open technical questions can still produce a partial, honestly-marked task list.

The three standards and the spec are the **stable prompt prefix** — they change rarely, so the fixed read order above keeps caching effective.

**--- CACHE BOUNDARY — read the per-run-changing input below only after the stable prefix above ---**

3. If `specs/<epic-slug>/tasks.md` already exists, read it — this is a re-run. Preserve existing task IDs and any human edits (Hard Rules 3 and 5); fold spec changes in as new tasks or as status/step updates, never by renumbering.

### Phase 1 — Decompose

Break the spec into tasks. A trivially small epic (≤2 files, ≤2 endpoints, no new integration, no new table, ≤3 ACs) may collapse to a single task — note `decomposition skipped (small epic)` in Scope and skip the Task Planning Questions.

#### Decomposition rules

1. **One task = one cohesive, test-first unit** completable in a single `implement-epic` pass. If it needs >3 file edits across different layers, split it.
2. **Prefer vertical slices** ("endpoint + validation + service + repository for one behaviour") over horizontal layers ("all controllers", then "all services").
3. **Extract cross-cutting / setup work into Foundation Tasks** — a DB migration when >1 table, security config for new auth, infra/setup for a new dependency, and project scaffolding (CI, `logback-test.xml`, the Maven quiet-flag config, ArchUnit rules). These map to `Foundation`, not an AC.
4. **Respect the spec's ordering** — if the Implementation Plan gives explicit ordering, honour it. If a spec section carries `[blocked by TQ-n]`, still create the task, set `Status: blocked`, and reference the TQ (Hard Rule 4).
5. **Map every AC to at least one task**; one task may cover several related ACs.

#### Task Planning Questions (only when decomposition is genuinely ambiguous)

Present a questionnaire ONLY when the spec leaves a real fork in how to decompose. Same conventions as the rest of the pipeline: 2–5 options, `(select one)`/`(select all that apply)`, exactly one `← recommended` text label (never pre-checked), unchecked boxes always `[ ]` never `[]`. Otherwise state the assessment inline and proceed.

```
## Task Planning Questions for <epic-slug>

1. Database migration handling: *(select one)*
   [ ] Separate Foundation task for migration + entity  ← recommended for >1 table
   [ ] Fold migration into the first implementing task (1 table / simple schema)

2. Layer separation: *(select one)*
   [ ] Vertical slices (endpoint → service → repository per behaviour)  ← recommended for features
   [ ] Horizontal layers (all controllers, then all services)  — refactoring only
```

### Phase 2 — Write tasks.md

Write `specs/<epic-slug>/tasks.md` with these sections:

1. **Header** — epic id, spec path, generated date, and the spec's Confidence (informational).
2. **Readiness Score** — computed (formula below) plus a one-line reason.
3. **Scope** — one paragraph: what this task list covers, plus any `decomposition skipped` note.
4. **Foundation Tasks** — scaffolding / cross-cutting tasks that map to `Foundation`, not an AC.
5. **Tasks by AC** — the implementing tasks, ordered so dependencies come first.
6. **Dependency notes** — the execution order and any notable chains; flag missing standards here.
7. **Blocked tasks** — tasks with `Status: blocked`, each naming the `TQ-n` (or other reason) blocking it.
8. **Task Planning Questions** — any open questions from Phase 1 (omit the section if none).
9. **Decision Log** — any planning choice that diverged from a `← recommended` option.
10. **Iteration History** — newest-first dated entries on each re-run.

#### Task block format

Every task — Foundation or AC — uses exactly this block:

```
### TASK-epic-01-01: <short title>
Maps to: AC-001            (or "Foundation")
Depends on: TASK-epic-01-02, TASK-epic-01-03   (or "none")
Status: not started        (plan-tasks sets only "not started" or "blocked")
Test-first step: <the failing test that gets written first>
Implementation step: <the minimal change that makes it pass>
Standards refs: <_coding-guidelines.md / _architecture-reference.md sections, or SWA_101 §N / SAW_102 §N; or "none">   (optional hint for implement/verify)
Files affected: <best-effort paths>   (optional hint)
```

`Status`, `Test-first step`, and `Implementation step` are the fields `implement-epic` runs its TDD loop against; `Maps to` and `Depends on` are what it and `verify-epic` order and trace by.

### Phase 3 — Validate

Before finishing, check:

1. **AC coverage** — every acceptance criterion in the spec is claimed by at least one task's `Maps to`.
2. **Dependency graph** — every `Depends on` id exists; no cycles.
3. **Test-first present** — every non-blocked task has a concrete `Test-first step` and `Implementation step`.
4. **Standards read** — if any `.claude/_*.md` were missing, the recommendation to run `set-standards` is recorded in Dependency notes.

Reflect any gap in the Readiness Score reason rather than hiding it.

## Readiness Score Formula

```
readiness = (tasks with a defined test-first step AND implementation step, and not blocked
             / total tasks) × 100
```

Report as: `Readiness: 90% — 1 task blocked by TQ-1`. Computed after the task list is populated, never asserted. Not a gate — an honest partial list with a low score is a legitimate output.

## Task ID Derivation

```
TASK-<epic>-<seq>

where:
  <epic> = the epic id, lowercased — e.g. EPIC-01 → epic-01   (NOT the full slug)
  <seq>  = 01, 02, 03, … zero-padded to 2 digits, in creation order
```

→ `TASK-epic-01-01`, `TASK-epic-01-02`, … IDs are stable handles: on a re-run keep existing IDs and only append new ones (Hard Rule 3).

## Hard Rules

1. Never create a task that traces to neither a spec acceptance criterion nor an explicit `Foundation` need.
2. Never write `in progress` or `done` — plan-tasks sets only `not started` or `blocked`; advancing status is `implement-epic`'s job alone.
3. Never renumber or reuse existing task IDs on a re-run — they are stable references other skills (and, optionally, Jira) point at.
4. Never invent an answer to an unresolved Technical Question to unblock a task — create the task `blocked` and reference the `TQ-n`.
5. Never emit JSON or write anywhere but `specs/<epic-slug>/tasks.md` — one Markdown file.
6. Always compute the Readiness Score — even if 100%.
7. Always order tasks by dependency, not spec/doc order.
8. `plan-tasks` never calls a Jira (or any ticketing) MCP tool and never creates or updates external tickets — Jira sync is a separate, human-triggered step (see below).
9. Always write unchecked questionnaire boxes as `[ ]` (never `[]`), with exactly one `← recommended` text label, never pre-checked.

## Exit Criteria

Skill is done when:
1. `specs/<epic-slug>/tasks.md` is written with all sections above.
2. Every spec acceptance criterion maps to at least one task.
3. The dependency graph is valid (all ids exist, no cycles).
4. The Readiness Score is computed and explained.
5. Any blocked tasks are listed under Blocked tasks with their `TQ-n`.

## Consumption Contract

### implement-epic

1. **Order** — execute tasks in topological order of `Depends on` (a task starts only once its dependencies are `done`).
2. **Status** — only `implement-epic` writes status, moving a task `not started → in progress → done` (or `blocked`). It reads the current `Status` line to know where to resume.
3. **TDD** — the `Test-first step` is the failing test to write first; the `Implementation step` is the minimal code to pass it.
4. **Standards / files** — `Standards refs` and `Files affected`, when present, focus which rules to honour and where the code and tests live.

### Jira sync (separate, human-triggered step — NOT this skill)

`plan-tasks` produces only the `tasks.md` artifact. Syncing tasks to Jira is a distinct, explicitly human-triggered action (per CLAUDE.md, ticket creation happens after `plan-tasks`, never automatically). When that step runs, each `### TASK-` block maps naturally to a Jira issue — id → traceability label, title → summary, `Maps to`/`Depends on` → issue links, `Status` → workflow state. This skill performs none of that and calls no ticketing MCP (Hard Rule 8).
