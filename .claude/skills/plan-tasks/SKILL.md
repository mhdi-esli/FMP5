# Plan Tasks Skill

Turn one epic's completed technical spec into an ordered, dependency-aware
list of implementable tasks. Each task must be small enough for one test-first
unit of work and traceable to an acceptance criterion or an explicit
Foundation need.

## Pipeline Position

`brainstorm` → `brainstorm/Epic_PRD.md` → `write-spec` →
`specs/<epic-slug>/spec.md` → `plan-tasks` →
`specs/<epic-slug>/tasks.md` → `implement-epic`

This skill plans work only. It never implements code, changes external tickets,
or invokes the next pipeline stage.

## File Layout

```
{project root}/
├── brainstorm/Epic_PRD.md             (source of epic IDs, via Epic Breakdown)
├── .claude/_architecture-reference.md (input, from set-standards, if present)
├── .claude/_coding-guidelines.md      (input, from set-standards, if present)
├── .claude/_documentation-standards.md (input, from set-standards, if present)
├── specs/<epic-slug>/spec.md          (input, produced by write-spec)
├── specs/<epic-slug>/tasks.md         (only output, generated by this skill)
└── .claude/skills/plan-tasks/
    └── SKILL.md
```

## Input

`Epic name` is required. It must match an `EPIC-NN` entry in
`brainstorm/Epic_PRD.md`'s Epic Breakdown, and that epic must already have a
`specs/<epic-slug>/spec.md`.

Resolve the epic to the same existing `<epic-slug>` used by `write-spec`. Do
not derive a competing slug. If the epic is absent or ambiguous, ask the user
to identify it. If its spec does not exist, stop and report:

`No spec found for this epic. Run /write-spec <epic> first.`

Never plan directly from the PRD, skip `write-spec`, or improvise a spec.

## Workflow — State Machine

### Phase 0 — Preflight

After resolving the existing epic slug, read in this exact fixed order. Never
use a directory glob or directory-listing order for these inputs; the fixed
prefix preserves prompt-cache reuse across runs.

```
1. .claude/_architecture-reference.md   (if present)
2. .claude/_coding-guidelines.md        (if present)
3. .claude/_documentation-standards.md  (if present)
4. specs/<epic-slug>/spec.md
-- CACHE BOUNDARY: standards and spec above are stable for this run; the
   existing task list below is the evolving reconciliation input --
5. specs/<epic-slug>/tasks.md            (only if it already exists for a re-run)
```

Follow all applicable conventions in items 1–3. If any is missing, continue but
add a note under **Risks** recommending that `set-standards` be run before
further epics are built. Do not mark otherwise ready tasks blocked.

Confirm the spec exists before continuing. Extract:

- epic ID and name;
- spec version marker, preferring the latest explicit version in Iteration
  History when present;
- the spec's Confidence Level;
- Acceptance Criteria Mapping;
- Implementation Plan;
- Technical Questions and their current resolution state; and
- facts needed by test-first and implementation steps.

Put the spec's Confidence Level in the task-list header for information only.
Never use it as a generation gate. A spec with open technical questions may
produce a partial, honestly blocked task list.

If `tasks.md` exists, this is a Phase 2 re-run. Preserve its stable task IDs,
statuses, planning decisions, and prior iteration history while comparing task
definitions with the current spec.

### Phase 1 — Draft

This phase always runs and never blocks the whole task list because information
is missing.

#### Step 1 — Decompose

Walk both the Acceptance Criteria Mapping and Implementation Plan. Decompose
the required work into cohesive tasks small enough to complete as one
RED → GREEN → REFACTOR unit in `implement-epic`.

Apply these rules:

1. Every implementation task must use `Maps to: AC-NN`, referring to an AC in
   the spec. One AC may require multiple tasks, and one task may map to multiple
   closely related ACs when one test-first unit genuinely covers them.
2. Work that does not map to an AC but is explicitly required to enable the
   implementation belongs under **Foundation Tasks** with
   `Maps to: Foundation`. Examples include scaffolding, configuration, CI, and
   test infrastructure. Maven quiet-output configuration and
   `logback-test.xml` belong here in whichever epic first requires them.
3. Prefer cohesive behavioral or vertical slices over broad horizontal batches.
   A task must name one concrete failing test or smallest coherent test set and
   the minimal implementation that makes it pass.
4. Derive every specific assertion, API, library call, configuration value, or
   implementation detail from the spec, PRD, or a resolved Technical Question
   or Task Planning Question. Do not add specificity that the source material
   does not support.
5. If required detail is unresolved, still create the implied task and set
   `Status: blocked`. Name the exact `TQ-n` or task-planning question in the
   task's Test-first and/or Implementation step rather than inventing an answer.
6. Treat `[blocked by TQ-n]` as a current block only if that TQ remains
   unresolved in the spec's authoritative Technical Questions or Decision Log.
   If it has been resolved, plan from the recorded resolution and do not carry
   forward a stale prose marker.
7. Order tasks by dependency rather than document order. If task B requires
   task A's output, A appears earlier and B lists A under `Depends on`.
8. Ensure every AC in the spec maps to at least one task, including ACs whose
   tasks are blocked.
9. Do not create speculative cleanup, refactoring, or infrastructure tasks not
   grounded in the source material.

For a first run, assign stable IDs in creation/dependency order:

```
TASK-<epic>-<NN>

<epic> = lowercase epic ID, e.g. EPIC-01 → epic-01
<NN>   = zero-padded sequence: 01, 02, 03, ...
```

Examples: `TASK-epic-01-01`, `TASK-epic-01-02`.

A newly generated, unblocked task receives `Status: not started`; a task with a
named unresolved blocker receives `Status: blocked`. These are planning states,
not progress inferred from the codebase. Never assign `in progress` or `done`.

#### Step 2 — Compute Readiness

Only after decomposition, compute:

```
readiness = (
  tasks with fully defined test-first and implementation steps and not blocked
  / total tasks
) × 100
```

Count Foundation and AC tasks alike. A task is ready only when both steps are
specific enough to execute and its status is not `blocked`. Use the actual task
states; never estimate or fabricate the score.

Report the numerator, denominator, percentage, and one-line reason for any
shortfall, for example:

`Readiness: 83% — 10 of 12 tasks ready; 2 blocked pending TQ-2.`

Readiness is informational. It never prevents writing `tasks.md`.

#### Step 3 — Write tasks.md

Write `specs/<epic-slug>/tasks.md` regardless of readiness. It is the only
artifact this skill creates or updates.

### Phase 2 — Re-run

When `tasks.md` already exists because the spec changed or questions were
resolved:

1. Never renumber, reuse, or reorder the identity of an existing task ID. Keep
   IDs stable because commits, pull requests, and `implement-epic` reference
   them. Assign each new task the next unused numeric suffix for the epic.
2. Preserve every existing task's `Status` field. Status normally belongs to
   `implement-epic` or the user, not this skill.
3. The sole status transition `plan-tasks` may perform on re-run is
   `blocked` → `not started` when the exact Technical Question or Task Planning
   Question that blocked the task is now explicitly resolved. Record the
   resolution reference and unblock in Iteration History.
4. Never change `not started`, `in progress`, or `done` based on source-code
   inspection or regenerated planning. Never revert a task to `blocked`
   silently; if changed requirements introduce a new blocker for an existing
   progressed task, preserve its status and flag the conflict under Blocked
   Tasks for human resolution.
5. Regenerate an existing task's title, mapping, dependencies, test-first step,
   or implementation step only when its underlying spec section actually
   changed. Preserve unaffected text exactly.
6. Append a dated Iteration History entry describing each substantive task
   definition change, task addition, new blocker, or unblock. Never silently
   rewrite history.
7. Preserve earlier Task Planning Questions and Decision Log entries. Update
   them only when an answer or decision has actually changed.
8. Recompute Readiness from the updated task states after all reconciliation.

## Task Format

Every Foundation or AC task uses this exact field structure:

```markdown
### TASK-<epic>-<NN>: <short title>
Maps to: AC-03
Depends on: TASK-epic-01-02, TASK-epic-01-04
Status: not started
Test-first step: <the failing test written first>
Implementation step: <the minimum change that makes it pass>
```

Use `Maps to: Foundation` for Foundation tasks and `Depends on: none` when
there are no dependencies. Multiple ACs may be comma-separated only when the
unit genuinely covers each one.

`Status` is a plain field, not a checkbox. On first generation, its value is
`not started` or `blocked` based on an explicit blocker. On re-run, preserve it
according to Phase 2. `implement-epic` or a human owns progress states.

For blocked work, identify the blocker in the executable fields:

```markdown
Status: blocked
Test-first step: Blocked by TQ-2 — test contract cannot be selected until <question> is resolved.
Implementation step: Blocked by TQ-2 — implementation shape depends on the recorded answer.
```

## Task Planning Questions

Most design decisions should already be settled by `write-spec`. Raise a Task
Planning Question only when decomposition itself requires a human choice, such
as whether tightly coupled migration and endpoint work should be one unit or
two and the spec does not decide it.

Use the same questionnaire conventions as `brainstorm` and `write-spec`:

- 2–5 options;
- `(select one)` or `(select all that apply)`;
- exactly one option may include the text label `← recommended`;
- never pre-check the recommended option;
- unchecked boxes are always `[ ]`, with a literal space, never `[]`; and
- any checkbox other than `[ ]` or `[x]` is malformed and remains unanswered.

Example:

```markdown
## Task Planning Questions

### TPQ-1: Migration task boundary *(select one)*

[ ] Keep migration and endpoint in separate tasks ← recommended
[ ] Keep migration and endpoint in one task
```

If a Task Planning Question is unanswered or malformed, include it in the
output and mark every affected task `blocked` pending its `TPQ-n`. Continue
planning unaffected tasks.

When an answer diverges from the recommended option, add one Decision Log
entry with the selected answer and rationale. Do not log ordinary selections
that follow the recommendation.

## Required tasks.md Sections

Write sections in this order:

1. **Title and metadata** — epic ID/name, epic slug, spec path, spec version,
   spec Confidence Level, and generated/updated date.
2. **Readiness Score** — computed percentage, numerator/denominator, and reason
   for shortfall.
3. **Scope** — the epic and exact spec version used.
4. **Foundation Tasks** — cross-cutting work with `Maps to: Foundation`; write
   `None` when there are no Foundation tasks.
5. **Tasks by Acceptance Criterion** — one subsection for every AC in the spec,
   with tasks in dependency order within each group.
6. **Dependency Notes** — non-obvious dependency chains and tasks that may run
   in parallel. Do not duplicate every `Depends on` field.
7. **Blocked Tasks** — consolidated list of each blocked task and its exact
   `TQ-n` or `TPQ-n`; write `None` when no task is blocked.
8. **Task Planning Questions** — include only if any arose during decomposition.
9. **Decision Log** — deviations from recommended Task Planning Question
   choices; write `None` when there are none.
10. **Risks** — missing shared standards, source conflicts, and planning risks;
    write `None` when none remain. A missing standards file is a Risk, not a task
    blocker.
11. **Iteration History** — dated initial generation and re-run entries, each
    describing what changed.

## Validation Before Exit

Before completing the skill, validate the generated or updated task list:

1. Every spec AC is represented by at least one valid `Maps to` field.
2. Every non-Foundation AC reference exists in the spec.
3. Every `Depends on` task ID exists, appears in a valid dependency order, and
   the graph has no cycles.
4. Every task maps to an AC or Foundation.
5. Every ready task has fully defined Test-first and Implementation steps.
6. Every blocked task names a specific unresolved `TQ-n` or `TPQ-n`.
7. Existing task IDs and protected statuses were preserved on re-run.
8. Readiness arithmetic matches current task states.
9. All unchecked questionnaire boxes use `[ ]`.
10. The output path is exactly `specs/<epic-slug>/tasks.md`.

Fix validation defects in the task list before exiting. Do not solve unresolved
questions merely to make validation pass.

## Exit Criteria

The run is complete when `specs/<epic-slug>/tasks.md` has been written or
updated with:

- an accurate Readiness Score;
- every task mapped to an AC or Foundation;
- dependency-safe ordering and valid references;
- executable test-first and implementation steps for every ready task; and
- an explicit question reference for every blocked task.

`Readiness ≥ 90%` is not an output condition. It is a downstream consideration
for `implement-epic` or a human deciding whether to begin the whole epic or
only its ready tasks.

## Hard Rules

1. Never mark a task `done` or `in progress`; those progress states belong to
   `implement-epic` or the user. Preserve them unchanged on a re-run.
2. Never renumber or reuse an existing task ID.
3. Never silently remove a blocked state. Unblock only when its exact question
   is explicitly resolved, and record the reference in Iteration History.
4. Never invent an answer to unblock a task at the spec or task-planning level.
5. Never fabricate Readiness; compute it from actual task states after
   decomposition and reconciliation.
6. Always write unchecked boxes as `[ ]`, never `[]`. Treat malformed checkbox
   syntax as unanswered.
7. Never introduce a fact, figure, library call, assertion, or configuration
   value that cannot be traced to the spec, PRD, or a resolved Technical or
   Task Planning Question.
8. Never call Jira or any ticketing MCP tool and never create or update
   external tickets. Jira synchronization is a separate, explicit human action
   after review of `tasks.md`.
9. Always read Phase 0 inputs in the fixed order; never use a directory glob.
10. Never write task output anywhere except
    `specs/<epic-slug>/tasks.md`.
11. Never plan directly from `brainstorm/Epic_PRD.md` when the required spec is
    missing.
